# Review: candidate construction, leakage control, evaluation

**Date:** 2026-09-04. **Scope:** `sentinel/detect/`, `sentinel/eval/`,
`sentinel/graph/window.py`, `sentinel/learn/`, plus a scan of comparable public
work. **Nothing here was measured in this pass** — every claim is either read
directly off the code, quoted from an existing measurement in `docs/`, or

## 1. The one finding that is a defect rather than an opportunity

### The ground-truth label is reachable from the detect path

`PairAgg` carries a `laundering` counter, incremented from
`batch.is_laundering` on every edge insert and decremented on expiry
(`sentinel/graph/window.py:53-66, 116, 142`). `WindowedGraph.subgraph_edges`
returns `(src, dst, agg)` triples — **the whole `PairAgg`** — and those triples
are handed to `motifs.build_digraph` and to `features.build` as
`internal_edges` (`sentinel/detect/candidates.py:160-168`).

Grepped: no module under `sentinel/detect/`, `sentinel/learn/` or
`sentinel/report/` reads `.laundering` today. The only reference outside the
graph module is an assertion in `tests/test_phase1.py:60`.

So this is not an active leak. It is an **unguarded surface**, and it is the
same shape as the one rule 6 exists for: a future feature — or an
autocompletion — that writes `agg.laundering` gets a perfect detector and a
green test suite. The repository's own standard is that a boundary like this is
a mechanised property with a negative control, not an intention.

The fix is idiomatic and cheap, and has two halves:

- **Static.** Extend the AST walk in `tests/test_measured_path_closure.py` to
  flag `Attribute(attr="laundering")` anywhere reachable from a measured entry
  point, with `tests/test_phase1.py` as the negative control.
- **Runtime.** A poison test: randomise `.laundering` on every edge in a
  fixture, regenerate, and assert every candidate key, score and rank is
  bit-identical. This catches what the static walk cannot — a label read through
  an alias or a `getattr`.

The cleaner long-term shape is for `subgraph_edges` to yield a label-free view,
but the poison test is worth having regardless, because it is the check that
cannot be defeated by a rename.

## 2. Candidate-graph construction

The design is well-argued and the reasoning is recorded where it happened.
Four observations, in decreasing order of how much they matter.

### 2a. The seed rule is the largest structural loss, and it is not a scoring problem

`CandidateGenerator.seeds` fires only on accounts that are pass-through in the
window. `sentinel/eval/funnel.py`'s docstring already records the consequence:
BIPARTITE / FAN-OUT / RANDOM / STACK generate **0%** because they contain no
pass-through account by construction.

This bounds recall before any of the scoring work is reached, and it is
consistent with everything the seed-cheat diff found — the cheat's advantage is
about the pool *containing* the ring, and `size`, which reads no features,
collects the same 2.25× prize as the shipped blend.

The natural second predicate is already half-built: `detect/layers.py` computes
the block-density read that GARG-AML ([B-Deprez/GARG-AML](https://github.com/B-Deprez/GARG-AML),
[arXiv:2506.04292](https://arxiv.org/abs/2506.04292)) turns into a single
per-node score over the second-order neighbourhood. That score is defined for
every node, including ones with no pass-through, which is exactly the gap. It
is queued as S1, with a degree-burst control arm (S2) so the prize is
attributable to the idea rather than to "more seeds".

**The kill rule matters more than usual here.** A seed rule that fires on
everything raises seeded-recall and destroys the funnel's meaning. S1's
pre-registration must fix a seed-count budget in advance.

### 2b. Suppression couples the scorer to the candidate set

`suppress()` is greedy non-maximum suppression **ordered by score**, run inside
`generate()`. `HANDOFF-NEXT.md` already records the consequence — a weight
change invalidates the pool, and `--rescore` makes a stale pool internally
consistent rather than correct.

Worth naming the stronger version: this makes **every scorer A/B structurally
confounded**. Ordering the suppression by a score-free deterministic key
(largest member set, tie-broken on `canonical_key`) would decouple the two, at
the cost of no longer keeping the highest-scoring representative. That is a real
cost and the headline would move. The argument for doing it anyway is that the
resulting numbers are *interpretable*, which the current ones are not. Queued as
B3, and it should be run as a diagnostic before it is considered as a change.

### 2c. Fragment linking is the direction the evidence points at, and BlazingAML has the shape

`PHASE2-SEED-CHEAT-FINDINGS.md` §H2 is the strongest result in the repo:
**51% of cheat-rescued rings are split across ≥2 components of their own
induced subgraph** against 5.7% of recovered ones. The seed is present and
stranded. H3 refutes budget as the fix, and refutes it *backwards* — more reach
means more containment and less coverage.

[BlazingAML](https://arxiv.org/abs/2604.12241) is the closest public work on
mechanism. It builds patterns as compositions of neighbourhood expansion, set
intersection and set difference with temporal break conditions, rather than
expanding a neighbourhood and searching inside it — a scatter-gather is found by
intersecting the out-neighbours of A with the in-neighbours of B, which
constructs the shape directly instead of hoping expansion happens to contain
it. It reports F1 identical to GFP at 210–333× the throughput.

Applied here, that suggests fragment linking should be **shape-directed rather
than proximity-directed**: join two candidates when a bounded set intersection
says they are two ends of one pattern, not merely when they are close. Queued as
B1, with the standing requirement that containment and Jaccard are reported
together — linking grows candidates, and candidate size is a measured confound.

### 2d. Two smaller things in the motif layer

- **`MAX_CYCLES = 200` makes cycle features order-dependent when it binds.**
  `find_cycles` truncates `nx.simple_cycles` in enumeration order, so on a dense
  subgraph `n_cycles`, `max_cycle_len` and `nodes_in_cycles` reflect
  enumeration order rather than the graph. Deterministic across runs — the
  determinism gate will pass — but not unbiased. Worth either a recorded
  known-limit or a length-stratified cap (collect up to *n* per cycle length).
- **Cycles have a temporal validity test but no temporal window.** Scatter-gather
  was correctly bounded at 6h with the unbounded count kept alongside so the
  difference stays measurable (`SCATTER_GATHER_WINDOW_MINUTES`). The identical
  argument applies to cycles: a loop closing over 72 hours and one closing in an
  afternoon are different objects. `is_temporally_valid` accepts both.

## 3. Label-leakage control

This is the strongest part of the project, and the seed-cheat work is
genuinely better than most published practice — the cheat is quarantined behind
an explicit `seed_override` that the real path never uses, the arms are paired
on the same held-out cycles, and `docs/CENTREPIECE-INVALIDATED.md` records a
pre-registered kill rule firing against the project's own centrepiece.

Two things remain open, both already half-acknowledged in the code.

### 3a. The split is time-ordered on negatives only

`ring_time_split` asserts that no training negative post-dates any test
negative, and deliberately lets a train-assigned ring keep the candidates it
produced after `split_t` — ring identity beats time-ordering, because two
near-duplicate views of one ring on opposite sides of the boundary is the worse
leak. The trade is correct and the docstring is honest that an earlier version
of the claim was an overclaim.

The standard technique for having both is a **purged split with an embargo**:
drop every record within a gap either side of the boundary, so no train record
is temporally adjacent to a test record regardless of which ring it belongs to.
It costs training rows — which matters here, since the all-positive query-group
fix already cost 156 of 321 training positives — but it converts a documented
caveat into an asserted property. Queued as L2, to be **reported beside** the
current split rather than replacing it.

### 3b. Confounded comparisons

The run-1 vs Phase-4 "2×" differs on five axes at once (feature count,
~250× training-set size, split rule, split point, evaluation window), and
`eval_oracle.py` says so at length and quotes no literal on purpose. That is
the right handling. The clean label-tax experiment (R1) remains the only thing
that resolves it, and it has been open since `HANDOFF-NEXT.md` §3.

## 4. Evaluation methodology

Rule 5's restatement is correct and the reasoning is right: p@k trials do not
nest in rings, so ring-clustering p@k is undefined rather than stricter; where
trials *do* nest in rings, the wider interval is reported. Reporting the 0.0890
ring-clustered width over the 0.0396 cycle-clustered one is the direction that
costs the project something, which is the mark of a real rule.

Three gaps, all cheap.

### 4a. `is_hit`'s thresholds are unreported free parameters

`HIT_SHARE = 0.5` and `MIN_JACCARD = 0.3` determine every headline number in
the repository. The reasoning for having a Jaccard floor at all is documented
and correct (containment alone let a node-count baseline tie the real score).
The *values* are not defended by a curve.

This is the single cheapest credibility win available: report p@10 and
built-recall over a 3×3 grid, once, as a band beside the headline. It costs
about two hours and permanently closes "you tuned the floor" — an objection
this project will otherwise get asked, precisely because it is so careful
everywhere else. Queued as M1.

### 4b. No family-wise accounting

Five phases, dozens of 95% intervals, and no record of how many comparisons
were made. `prereg/` already separates pre-registered from post-hoc, which is
the hard half. The missing half is a count: when a result is surprising, the
number of post-hoc comparisons behind it belongs beside it.

### 4c. The bootstrap's own Monte Carlo error is unacknowledged

Every `bootstrap_ci` call uses `seed=7`, `n_resamples=2000`. At n=18 cycles that
is almost certainly fine, but "almost certainly" is not the standard here.
One headline re-run at a second seed and 10,000 resamples settles it in
minutes. Queued as M2.

## 5. Prior art, and what is genuinely new here

| work | relation |
|---|---|
| [IBM/Multi-GNN](https://github.com/IBM/Multi-GNN) | The AMLworld reference baselines. Useful as the learned-model ceiling beside the oracle arm. |
| [B-Deprez/GARG-AML](https://github.com/B-Deprez/GARG-AML) | Already partly mirrored in `detect/layers.py`. The unused half is the per-node score — the candidate second seed predicate. |
| [BlazingAML](https://arxiv.org/abs/2604.12241) | Shape-directed construction by set intersection rather than expand-then-search. The most relevant published mechanism for the fragmentation problem. |
| [aidotse/AMLGentex](https://github.com/aidotse/AMLGentex) | Controllable generator — lets the window-vs-ring-size hypothesis (B2) be tested at chosen fragmentation rates instead of only at HI-Small's. |
| [IBM/AMLSim](https://github.com/IBM/AMLSim) | Older generator; a second dataset for the cross-domain test. |
| ["When Graph Structure Becomes a Liability"](https://arxiv.org/abs/2604.19514) | Transductive splits overstate GNN benefit under temporal shift on Elliptic. Read before any Elliptic2 headline. |
| [Elliptic2](https://arxiv.org/abs/2404.19109) | The subgraph-level framing `eval/dataset.py`'s static path targets. |

**What none of them have.** Every one of these reports a model number. None of
them report a *funnel* — per-typology recall at seed-reachable / seeded / built
/ ranked, with the admission that four typologies are at 0% by construction of
the seed rule. That decomposition, plus the practice of publishing the
refutations (`docs/negative-results/`) and letting a pre-registered kill rule
retire the project's own centrepiece, is the part of this work that has no
counterpart in the public repositories above. It is worth positioning on
directly rather than on p@10.

**No parity claim against any row of this table may enter the repo until the
head-to-head has been run on this machine.** `HANDOFF-NEXT.md` §1 records the
GFP comparison as blocked on the OS, not skipped; the same standard applies to
the rest.
